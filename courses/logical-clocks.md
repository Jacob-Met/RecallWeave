# Causal order with Lamport and vector clocks

A later number does not, by itself, prove a causal connection. This lesson builds the distinction from an event graph, calculates two kinds of logical timestamp, and uses them to separate causal order from concurrency.

## 1. Start with events and edges

An **event** is a local action, a send or a receive. The send of a message and its receipt are separate events, even when a diagram places them close together.

The relation *happens-before*, written `a → b`, is generated by:

1. **Program order:** an earlier event on a process precedes a later event on that same process.
2. **Message order:** sending a particular message precedes receiving it.
3. **Transitivity:** if `a → b` and `b → c`, then `a → c`.

Equivalently, there is a directed path from `a` to `b` in the event graph. A timestamp describes the graph; assigning a timestamp does not create its communication edges.

Two **distinct events are concurrent** when there is no directed path in either direction. Concurrency here describes the absence of a causal ordering in the complete model. It does not assert that the events happened at the same physical instant.

Keep these two statements separate:

- **Known concurrent:** the complete relevant event graph has no path in either direction.
- **Order unknown from the evidence:** the available observations do not establish a path, but relevant events or messages may be missing.

An isolated pair of unsynchronized wall-clock readings gives the second situation. It cannot establish physical order when offsets and error bounds are unknown, and it cannot establish concurrency when the communication history is missing. Lamport's original paper defines the event relation and distinguishes it from a physical-clock measurement.[1]

### A common ancestor does not order its descendants

Suppose A has `A1 → A2 → A3`, B has `B1 → B2 → B3`, and the only message edge is `A2 → B2`. Both A3 and B3 follow A2. Nevertheless, neither A3 nor B3 has a directed path to the other.

A path may follow arrows forward. It cannot travel backward from A3 to A2 and then forward to B3. Shared history alone does not make one later branch cause the other.

## 2. The complete worked execution

There are three processes, A, B and C. Their complete program orders and actions are:

| Process | Events in program order |
|---|---|
| A | A1 local → A2 send mAB → A3 local → A4 receive mCA |
| B | B1 local → B2 receive mAB → B3 send mBC |
| C | C1 local → C2 receive mBC → C3 send mCA |

The only message edges are:

| Message | Send | Receive |
|---|---|---|
| mAB | A2 | B2 |
| mBC | B3 | C2 |
| mCA | C3 | A4 |

Every local, send and receive action shown is one event. There are ten events. The presentation of rows does not introduce an order between different processes. Only the listed program-order edges, the three message edges and their transitive consequences count.

For example, `A2 → B2 → B3 → C2 → C3 → A4` is a path. A3 also precedes A4 through A's own program order, but no message carries A3 onward to B or C before C3.

## 3. Lamport clocks: an order-compatible number

Each process starts with scalar counter 0. Use this precise convention:

- At a local event or send, increment the local counter by 1.
- Record the resulting value as that event's timestamp.
- A send carries its recorded timestamp.
- At a receive, set the counter to `max(current local counter, received timestamp) + 1` and record that value.

The extra increment at a receive puts it strictly after both the receiving process's preceding event and the matching send. A process can skip scalar values after receiving a high timestamp. Skipped numbers are not a count of missing local actions or elapsed seconds.

### Calculate the three receives

For **B2**, B's previous event B1 left its counter at 1. Message mAB carries A2's timestamp 2:

`L(B2) = max(1, 2) + 1 = 3.`

B3 is the next send on B, so it increments to 4.

For **C2**, C1 left the local counter at 1 and mBC carries 4:

`L(C2) = max(1, 4) + 1 = 5.`

C3 then sends with timestamp 6.

For **A4**, A3 left A's counter at 3 and mCA carries 6:

`L(A4) = max(3, 6) + 1 = 7.`

### What the clock condition says

If `a → b`, then `L(a) < L(b)`. Every generating edge increases the clock, so every directed path does too.[1]

The converse does not hold: `L(a) < L(b)` does not prove `a → b`.

There is still a useful conclusion. If `L(a) = 4` and `L(b) = 9`, then **b cannot precede a**, because that would require `9 < 4`. Either a precedes b, or they are concurrent. Scalar order rules out the reverse causal direction without proving the forward one.

Two distinct events with equal valid Lamport timestamps cannot precede one another in either direction. If either direction existed, the clock condition would require a strict increase.

## 4. Vector clocks: retain the separate histories

Use one component per process, in the fixed order **[A, B, C]**. Every process starts with `[0, 0, 0]`.

For this lesson:

- A local event or send increments only the acting process's component.
- The event records the updated vector.
- A send carries that vector.
- A receive first takes the **componentwise maximum** of its current vector and the message vector, then increments the receiver's component once.

The maximum merges known histories without erasing information. The final increment records the new receive event. This is a precise choice of event-count convention; always establish a source's convention before comparing numeric examples.[2]

### B2: learn A's history and record B's receive

Before B2, B has `[0, 1, 0]`. Message mAB carries `[2, 0, 0]`.

`max([0, 1, 0], [2, 0, 0]) = [2, 1, 0].`

Increment B:

`V(B2) = [2, 2, 0].`

B3 increments B again and sends `[2, 3, 0]`.

### C2: carry the chain through B to C

Before C2, C has `[0, 0, 1]`. Message mBC carries `[2, 3, 0]`.

`max([0, 0, 1], [2, 3, 0]) = [2, 3, 1].`

Increment C:

`V(C2) = [2, 3, 2].`

C3 increments C again and sends `[2, 3, 3]`.

### A4: merge remote information with A's newer local history

Before A4, A has `[3, 0, 0]`. Message mCA carries `[2, 3, 3]`.

`max([3, 0, 0], [2, 3, 3]) = [3, 3, 3].`

Increment A:

`V(A4) = [4, 3, 3].`

The message's A component is only 2: its chain began at A2, before A3. Taking the maximum preserves A's own knowledge of A3 instead of replacing 3 with the stale 2.

### Full timestamp table

| Event | Action | Lamport timestamp | Vector [A, B, C] |
|---|---|---:|---|
| A1 | Local | 1 | [1, 0, 0] |
| A2 | Send mAB | 2 | [2, 0, 0] |
| A3 | Local | 3 | [3, 0, 0] |
| A4 | Receive mCA | 7 | [4, 3, 3] |
| B1 | Local | 1 | [0, 1, 0] |
| B2 | Receive mAB | 3 | [2, 2, 0] |
| B3 | Send mBC | 4 | [2, 3, 0] |
| C1 | Local | 1 | [0, 0, 1] |
| C2 | Receive mBC | 5 | [2, 3, 2] |
| C3 | Send mCA | 6 | [2, 3, 3] |

Within this event-count convention, a component records the included prefix of that process's history. A4's vector summarizes A's four events, B's three and C's three: all ten events including A4. Its strict causal past contains the other nine events.

## 5. Compare vectors carefully

Define `u ≤ v` when every component of u is at most the corresponding component of v. Define **strict vector order** `u < v` when `u ≤ v` and `u ≠ v`.

That means **all components are at most and at least one is strictly smaller**. It does not mean that every component must be strictly smaller.

With standard vector clocks over the complete event and message model, causal precedence and this strict vector order agree.[2] Consequently, distinct events with incomparable vectors are concurrent.

| Pair | Component comparison | Conclusion |
|---|---|---|
| A1 [1,0,0], A2 [2,0,0] | A grows; B and C stay equal | A1 precedes A2 |
| B3 [2,3,0], C2 [2,3,2] | C grows; A and B stay equal | B3 precedes C2 |
| A3 [3,0,0], B2 [2,2,0] | First has more A; second has more B | Concurrent |
| A3 [3,0,0], C3 [2,3,3] | First has more A; second has more B and C | Concurrent |
| C3 [2,3,3], A4 [4,3,3] | A grows; B and C stay equal | C3 precedes A4 |

A3 and C3 are the central scalar counterexample: their Lamport values satisfy `3 < 6`, but their vectors are incomparable and the graph has no path in either direction.

Neither adding vector components nor inspecting one chosen component gives the componentwise order. For `[3,1,0]` and `[2,2,0]`, even the equal sums conceal two incompatible histories.

Concurrency is also not transitive. In this graph, A1 is concurrent with B1, and B1 is concurrent with A2, while A1 precedes A2.

### A small completeness check

The ten events have 45 unordered pairs. Of those, 32 are causally ordered and 13 are concurrent. Listed once each, the concurrent pairs are:

`A1–B1, A1–C1, A2–B1, A2–C1, A3–B1, A3–B2, A3–B3, A3–C1, A3–C2, A3–C3, B1–C1, B2–C1, B3–C1.`

Only four of these concurrent pairs share equal scalar timestamps: A1–B1, A1–C1, B1–C1 and A3–B2. The other nine show that unequal scalar timestamps remain compatible with concurrency.

## 6. A total order can make a choice without discovering a cause

A system can sort events by **(Lamport timestamp, process ID)**, with a fixed process order A before B before C. In this model, each process's Lamport values increase strictly, so the pair uniquely orders these events.

The resulting order is:

`A1, B1, C1, A2, A3, B2, B3, C2, C3, A4.`

It respects every causal edge because causal edges already increase the scalar timestamp. It also chooses an order for concurrent events. Lamport describes this kind of extension from a partial order to a total order.[1]

A3 and B2 both have scalar timestamp 3. The process rule puts A3 first. Reversing the agreed process order puts B2 first. Neither convention creates a causal edge between them.

Do not treat the tie-break as a physical-time measurement. Do not treat it as an application-specific merge policy either. Sorting two concurrent document edits does not tell you whether they affect different fields, conflict on the same word, or require a human decision.

## 8. What this model assumes

This lesson uses a fixed, known set of three processes, a common component order, monotonically increasing counters and complete instrumentation of the relevant events and communications. There are no counter resets, omitted messages or reused process identities in the worked execution.

These assumptions matter. An out-of-band communication that is absent from the model can carry information the vectors do not record. Comparing unrelated vector namespaces, restarted counters or incomplete logs does not automatically inherit the conclusions established for this model.

Logical timestamps do not authenticate events, measure elapsed seconds, synchronize physical clocks or determine which document content is correct. Real systems need explicit decisions for identity, restarts, instrumentation and application behavior.
